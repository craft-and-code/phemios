# Concert discovery

Concerts displays JamBase v3 event dates directly in Phémios, independently of Aède authentication. Aède supplies canonical principal album artists; duplicate names across connected origins share a lookup. Event data remains attributed external claims. Navigation reads only cached results and local key/budget status, never JamBase.

## Credentials and explicit requests

Settings → External sources retains the user's JamBase API key in the device-private native `desktop.json`. It is excluded from browser preferences, account synchronization, portable backups and Aède overrides. IPC returns only presence and a validated budget summary. Configuration mutations acquire the shared budget lease before publication: an occupied or unreadable journal refuses the operation without silently changing the key. Saving/removing the new provider key also removes the retired provider credential; the former provider has no active client, form, credit or search handoff. Its disposable event cache is not reinterpreted as JamBase data.

Only an explicit concert search sends requests. Native HTTP permits the fixed `https://api.data.jambase.com/v3/quota` and `/events` endpoints, Bearer authorization in a header, no redirects/proxy, public resolved addresses, a 15-second timeout and two-MiB ceiling per response. Requests are sequential and spaced by at least one second. There is no automatic retry. A cancellation stops subsequent pages/artists; an in-flight quota/event pair can finish (up to two bounded requests), without updating a closed view.

## Free-tier ceiling

Before each event page, the unmetered `/quota` endpoint must report valid numeric usage, no overage, positive remaining quota and fewer than 1,000 used calls. Durable admission uses the smallest of 1,000, the effective provider quota and observed used-plus-remaining allowance; a stale response cannot repeatedly grant the last slot of a smaller or partially available quota. Invalid, refused, unavailable or exhausted quota stops the batch; hourly `RateLimit` headers are not substituted for subscription usage.

An additional device-wide journal limits attempted event requests to **1,000 over any rolling 32 days**, conservatively covering a monthly billing period without guessing its subscription anchor. This is intentionally stricter than a calendar-month reset. The protected `jambase-budget.json` is atomically published and synced **before** sending the event request. Failed/time-out attempts remain charged locally. A retained per-provider-period high-water counter also incorporates pre-existing observed account usage and advances before dispatch; a lagging quota response cannot grant the same final free slot twice. Confirmed local calls are not charged again when provider usage catches up. Shared usage first observed on this device is conservatively charged at observation time, so a new period never erases the rolling journal. Changing/removing a key, switching Aède accounts and restarting do not reset it. A cross-process file lease serializes admission through the quota check and HTTP operation. Malformed, public-permission, symlinked, busy or interrupted-publication stores refuse new event requests; detected clock rollback also refuses admission. No UI reset/import operation affects the journal. This is admission protection, not tamper-resistant DRM against a user deleting their own application data.

JamBase shares its subscription pool across keys, teammates, REST and MCP. Its Developer plan permits paid overages. A client cannot atomically prevent an unrelated application/device from consuming that shared pool between quota preflight and dispatch. **Dedicate the JamBase account to this Phémios installation** to use the local ceiling as a no-overage safeguard. The settings explain this boundary; the app neither subscribes nor upgrades a plan. Each separate installation has its own local journal. `/quota` itself is documented as non-metered. The trial has a total quota, not a monthly reset; the provider preflight remains authoritative when it is lower than the local allowance.

## Matching, attribution and incremental cache

`artistName` is a provider keyword filter, so results must additionally contain an exact normalized performer-name match. Names containing the provider's multi-value `|` operator are refused. Multiple provider IDs with the same name, including across pages, are ambiguous and refused. This does not claim name matching is a universal identity mapping. Event titles/tribute names alone do not match.

The native projection reads documented JSON-LD event fields, venue-local date/time, venue/country and event status; missing optional values stay unknown. Developer does not include ticket pricing, so no price is invented. Unmodified primary-ticket URLs (safe HTTPS only), falling back to the JamBase event URL, and a visible linked “Powered by JamBase” attribution with `rel="nofollow"` use the normal explicit browser handoff. Coverage follows JamBase inventory and the Developer plan's six-month upcoming window; it is not a guarantee of all worldwide shows.

At most ten 100-row pages are fetched per artist (one-based provider paging, zero-based IPC). Greater results are labelled partial. Each completed artist is immediately stored with retrieval time; failure/cancellation preserves earlier completed artists and prior answers. The provider-specific public cache is bounded to 200 artists/two MiB, expires oldest disposable answers only, contains no key/personal annotations and refuses corrupt data without overwriting it.

## Verification boundaries

Sibling Rust tests cover performer identity, one-based request mapping, Bearer header privacy, optional claims, durable reservation before dispatch, the blocked 1,001st attempt, shared-quota refusal, failed HTTP charging, restart/key replacement, concurrent leases, clock rollback, corrupt/symlinked/public stores and interrupted publication. Frontend tests cover status validation, pagination/cancellation, origin grouping and provider-separated cache. Storybook presents key/budget states without native IPC or a real credential. A user's valid API key is still required for live date/coverage acceptance.

Official contracts: [OpenAPI](https://data.jambase.com/openapi.json), [authentication](https://data.jambase.com/api/docs/authentication), [quota and limits](https://data.jambase.com/api/docs/rate-limits), [pricing](https://data.jambase.com/pricing).

The search toolbar remains available with a configured JamBase key even without an Aède session, including a cached catalogue. Concerts retains its static workspace import: opening it requires no deferred application-module fetch after the shell starts.

### Focused re-audit (2026-10-18)

A further source review follows neighboring quota/configuration call sites, provider projection, retained public cache, sequential pagination and native key consumers. No additional demonstrated JamBase defect is retained. Existing durable admission and key protections are unchanged. Added behavioral coverage confirms that cancellation after a page response starts no further page and that the production HTTP policy refuses a successful response exceeding its 2 MiB limit without echoing provider text. These fixtures use no live API key and spend no provider quota; they do not establish authenticated provider coverage or a shared-account global spending guarantee.
