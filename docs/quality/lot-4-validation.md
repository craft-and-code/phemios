## Runtime and cleanup contract

Acquisition runs on one private Tokio worker thread and bounds the entire connection/authentication/proxy/method phase to **one second**. Both session and system connections remain driven for the guard's lifetime. Synchronous creation waits at most two seconds for the result; a late result cannot leave an unowned guard active. No blocking nested runtime entry is used, including when the synchronous API is called from another runtime.

Known partial acquisition rolls back its display cookie and any acquired descriptors before returning the original error. Idle/sleep owned descriptors close first during cleanup. ScreenSaver UnInhibit is bounded to **500 ms**; each explicit connection close is bounded to **100 ms**. The synchronous destructor has a two-second reply bound and nonblocking private-runtime shutdown. Refused/timed-out cleanup emits a stderr diagnostic and closes the dedicated client connection; it no longer unwraps/panics. These are operation/wait budgets, not a hard real-time scheduling guarantee. Phémios still requests display=true, idle=true and sleep=false, preserving manual system sleep.

An unknown cookie after a timed-out Inhibit cannot be explicitly named for UnInhibit; the dedicated client connection is closed. The tests verify client disconnection, not a promise that every real desktop implementation correctly reclaims such a request. That desktop behavior remains an acceptance case. Drop cannot return an OS release result: cleanup diagnostics remain visible on stderr, while the existing frontend acknowledgement means the native command was handled, not proof that the desktop honored an inhibition/release.
