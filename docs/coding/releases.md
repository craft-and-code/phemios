# Native release preparation

The GitHub Release workflow follows Aède's separate App naming convention. Phémios has no CLI download: its private bundled Aède executable belongs to the App, while standalone Aède CLI releases remain in Aède's repository.

A push of a `vVERSION` tag builds installers on native macOS Apple Silicon, Windows x64 and Linux x86_64 runners. Ordinary branch pushes do not publish a release. Manual workflow dispatch builds downloadable Actions artifacts without publishing. Every expected installer must exist exactly once before packaging; ambiguous, missing or stale packages fail. SHA-256 sidecars accompany all downloads. The draft release is created only after every platform succeeds; a maintainer reviews it before publication. Version-specific notes in `docs/releases/vVERSION.md` supply its description, including exact per-system download/checksum links. The README badges link to the actual Release and Pages workflows; no badge claims an absent CI or security workflow.

The 0.3.0 preparation includes explicit maintainer authorization to commit, push, tag and make the verified installer release publicly downloadable. First validate all platforms with a manual run on `main`; only then push the annotated version tag. Review the tagged run and all installer/checksum assets before publishing its draft. A workflow rerun does not authorize moving a published tag or replacing prior assets. Campaign closure and release publication remain separate decisions.

Before tagging, align `Cargo.toml` workspace version, `package.json`, `package-lock.json` (root and root package), `src-tauri/tauri.conf.json` and Cargo lock workspace package versions. The release script checks npm/Cargo/Tauri agreement and tag equality. Browser preview identity reads the npm version; native HTTP clients read their Cargo package version, so they do not retain an older hard-coded release identifier. Cargo's locked build also checks its lockfile. Before compiling, the workflow resolves the latest published stable Aède release once and passes its tag/version/SHA to every platform. `scripts/audio-source.mjs` checks out that exact source, updates the shared dependency and lockfile, and fetches dependencies. Native preparation builds the bundled engine from the same selected source with `--locked --offline`, explicitly selecting the Rust host target and its source-local target directory so inherited Cargo output settings cannot substitute an old artifact; an old cached binary or a sibling checkout cannot substitute a different DSP. Development uses the same automatic policy. No manual pin edit is required after a stable Aède release.

A new workflow run, even for an old App tag, deliberately uses the latest stable Aède available when that run starts. Build logs, the workspace/lockfile, `.audio-source/selection.json` and bundled version metadata retain the selected SHA. API/network failure, moved release tags, modified cached sources and releases without shared audio fail before native compilation; no silent fallback is used. Native preparation requires network access even if dependencies are cached. Historical Aède v0.6.1 predates the shared crates; published v0.7.1 and later stable releases provide them. Select the latest actually published stable source rather than the technical bootstrap tag or a draft; record the exact selected SHA for each build/validation cycle.

The workflow overrides bundle targets explicitly: App and DMG on macOS, MSI/NSIS on Windows, and AppImage/DEB/RPM on Linux. The local `app` target remains unchanged. The current source configures macOS with Tauri’s ad-hoc signing identity (`bundle.macOS.signingIdentity: "-"`): Tauri signs the nested engine and the complete App before creating its DMG. `npm run build:native` checks the resulting App, and the Release workflow verifies both the App and its read-only DMG copy before checksums/uploads. Windows installers remain unsigned. Ad-hoc signing does not establish an Apple developer identity or notarization; Gatekeeper approval can still be required. The already published 0.2.0 assets remain unchanged until a separately approved new release. No updater keys, credentials, signing certificates or developer accounts are committed. Intel Mac and ARM Linux targets can be added after native CI and device acceptance are available.

Packaging policy is tested with temporary installer fixtures via `node --test tests/release.test.mjs`; those fixtures do not build or run an App. Separately, PH-STAB-001 C2 actually compiles/tests the Mac host, builds its App and workflow-equivalent DMG with published Aède 0.7.3, and verifies the image/packaged engine read-only; see [current validation](../quality/media-admission-validation.md). Those historical results do not establish 0.2.0 installer/runtime or signing/notarization acceptance. The new Release run and its artifacts provide their own native CI evidence; installed-platform, physical audio/device and provider acceptance remain separate. The earlier maintainer-reported Mac functional acceptance is recorded in [the PH-C09 ledger](../quality/ph-c09-validation.md#m-ph-c09-mac-01--maintainer-manual-functional-acceptance) against its original artifact, without reattribution to 0.2.0.

## macOS signature verification

Run `npm run build:native` for a signed host App and automatic verification. For a workflow-equivalent DMG, use `npx --no-install tauri build --ci --bundles app,dmg -- --locked`, then `node scripts/check-macos-bundle.mjs --dmg`. The checker uses the standard host release output at `target/release/bundle`; custom target/profile/output overrides need an explicitly adapted path and are outside this command's contract. `node scripts/check-macos-bundle.mjs --app "/path/to/Phémios.app"` checks a separately located bundle without altering it.

Both `app` and `dmg` targets are intentional: Tauri otherwise removes its intermediate App after building only the DMG, leaving no retained bundle to compare. The gate requires the expected identifier/version, a real CodeResources seal, successful `codesign --verify --deep --strict` on the whole App, and valid ad-hoc signatures for both native executables. It rejects linker-only signatures, missing/replaced sidecars and modified resources. For the DMG it mounts read-only without opening the App, checks the actual distributed copy and compares its sealed identity/executable/engine/resource hashes with the verified build. The mount is detached after success or rejection. A failed check prevents the Release workflow from naming, uploading or publishing installers.

`node --test tests/macos-bundle.test.mjs` exercises real compiler/codesign/DMG fixtures on macOS, including tampered resources, missing/modified engines and a substituted signed App. These cases require macOS command-line tools and intentionally skip elsewhere. Signature integrity checks neither launch the installed application nor establish hardware/audio, notarization or Windows/Linux acceptance. See [Tauri’s signing guidance](https://v2.tauri.app/distribute/sign/macos/).

## Human changes and commit history

Keep user-facing additions/fixes in [the next-release draft](../releases/unreleased.md) as work is implemented. Before the next approved tag, move its accepted changes into `docs/releases/vVERSION.md`, preserving the exact platform download and checksum links described above. Do not substitute a commit list for that summary or attribute pending work to a published release.

The publisher fetches complete history and runs `node scripts/release-notes.mjs vVERSION OUTPUT`. It requires matching manifests, an existing exact tag and completed version-specific notes, then appends every direct/merge commit since the latest reachable stable version tag (prereleases are excluded as baselines), with commit links and a comparison. The first release includes all history. `node --test tests/release-notes.test.mjs` exercises real temporary Git repositories; it does not publish anything.
